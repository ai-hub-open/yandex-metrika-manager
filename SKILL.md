# Yandex Metrika — аудит, анализ, управление

Метрика — это не «отчёты», а способ понять, что на самом деле происходит с продуктом после запуска. Скилл работает над одним счётчиком в **трёх режимах**:

- **Аудит** (по умолчанию) — разовая **read-only проверка, можно ли верить данным**: паспорт счётчика, качество данных, цели, разметка трафика, связка с Директом. Итог — HTML-отчёт «починить / проверить / норма». В счётчик не пишет.
- **Анализ** — ответ на конкретный вопрос («откуда заявки», «почему упала конверсия», «какая РК окупается») или **регулярный разбор** (неделя/месяц к прошлому периоду). Read-only. Итог — сводка в чат + файл, при регулярном разборе — состояние в папке на диске.
- **Управление** — **запись в счётчик**: цели и сегменты. Только под гейтом: проект изменений → `dry_run` → явное «ОК» → запись → журнал с before/after → проверка, что цель начала срабатывать.

Правка кампаний Директа — **не задача этого скилла**: аудит и ведение РК — `yandex-direct-audit`, создание РК — `yandex-direct-manager`. Из Метрики мы только **смотрим** на Директ (расход, клики, визиты, цели) и готовим для него цели и сегменты.

## Mode-gate (определяется первым делом)

| Сигнал в запросе | Режим |
|---|---|
| «проверь Метрику / счётчик», «аудит Метрики», «можно ли верить цифрам», «какие цели не работают», «правильно ли настроено» | **Аудит** |
| вопрос о данных: «откуда трафик», «какая кампания приносит заявки», «почему упало», «разбери за месяц», «сравни с прошлой неделей», «где теряем пользователей» | **Анализ** |
| «создай / поправь / удали цель», «настрой цели под Директ», «сделай сегмент для ретаргетинга», «приведи цели в порядок» | **Управление** |
| «продолжаем разбор», есть папка `metrika/<slug>/` с `pulse.md` | **Анализ (регулярный)** |

Противоречиво или неясно — **спроси одним вопросом**: «Проверить настройку счётчика, ответить на вопрос по данным или поменять цели/сегменты?»

Режимы стыкуются: аудит часто заканчивается предложением перейти в управление («3 мёртвые цели — переделать?»), анализ — гипотезами для A/B и ТЗ. Переход в управление — всегда **отдельный гейт**.

| | Аудит | Анализ | Управление |
|---|---|---|---|
| Запись в счётчик | никогда | никогда | только одобренное, через `dry_run` |
| Тулы | `*_get`, `report*` | `*_get`, `report*` | + `goals_add/update/delete`, `segments_add/delete` |
| Папка | `metrika/<slug>/audit/` | `metrika/<slug>/analysis/` | `metrika/<slug>/changes/` + `changes_log.jsonl` |
| Финал | `АУДИТ_МЕТРИКИ_<slug>.html` | сводка + `.md`/`.csv` | журнал + `change_report.md` |

## Принципы (для всех режимов)

1. **Сначала качество данных, потом выводы.** Корректность данных важнее количества отчётов. Если счётчик считает роботов, теряет треть визитов из Директа или цель срабатывает на каждом втором визите — любые выводы о конверсии ложны. Поэтому даже в анализе сначала идёт быстрый санити-чек (Шаг 0.5).
2. **Симптом ≠ причина.** «Упала конверсия» — симптом. Причина ищется разрезами: источник → страница входа → устройство → регион → шаг воронки. Не останавливайся на первом уровне.
3. **Объём ≠ качество.** Канал с большим трафиком и нулевой доходимостью до целей хуже маленького с высокой. Всегда смотри пару «визиты + конверсия/отказ/глубина».
4. **Каждый вывод = число + период + объём + сравнение.** Нет объёма (меньше ~100 визитов в сегменте или меньше ~10 достижений цели) — пиши «мало данных», не выдумывай.
5. **Атрибуция названа.** Метрика по умолчанию — последний значимый переход (`lastsign`). Пиши модель словами рядом с конверсиями; не сравнивай числа из разных моделей.
6. **Семплирование видно.** Если ответ помечен как семплированный — повтори с `accuracy: "full"` для ключевых цифр или явно пометь приближённость.
7. **Сырьё — в файлы, в чат — 5–10 строк.** Ответ тула идёт через контекст; тяни только нужные поля и строки (`limit`, `filters`).
8. **Вывод → действие.** Наблюдение без «что сделать, кто, какой ожидаемый эффект» — не находка. Для разработки — ТЗ (контекст, гипотеза, ожидаемый эффект), для маркетолога — конкретное действие.
9. **Ограничения — честно.** Чего не смогли проверить (нет доступа, нет целей, нет связки с Директом) — отдельный блок.

## Scripts

Все — стандартная библиотека Python, без сети. Запуск из корня скилла: `python -m scripts.<имя> ...`

**Где что лежит.** Рабочая папка `metrika/<slug>/` — в текущей папке пользователя, **не внутри скилла**. Раз скрипты запускаются из корня скилла, пути к рабочим файлам передавай абсолютные (`--input <абсолютный путь>/metrika/<slug>/audit/findings.json`). Скилл, установленный плагином Claude Code, при обновлении заменяется целиком: всё, что легло в его папку, пропадёт вместе с данными клиента.

- `metrika_table.py` — ответ `yandex_metrika_report` (JSON) → CSV + производные (CR, CPA, доля), фильтр по минимальному объёму, сравнение двух периодов (`--compare`) с дельтами.
- `goals_health.py` — ответ `goals_get` со `stats_days` → классификация целей: мёртвая / шумная / живая / мало данных, дубли условий, цели без ценности, нейминг.
- `utm_hygiene.py` — отчёт по UTM-меткам → разнобой регистра и написания, нестандартные `utm_medium`, рекламный трафик без меток.
- `ab_calc.py` — размер выборки и длительность A/B-теста по базовой конверсии, минимальному эффекту и трафику.
- `changes_log.py` — append-only журнал записей в счётчик (before/after, откат). Только Управление.
- `render_report.py` — `findings.json` → самодостаточный HTML-отчёт аудита.

## Архитектура: оркестратор + субагенты

Оркестратор (этот файл) держит скоуп, `_state.json`, гейты и сборку отчёта. Три тяжёлых сбора вынесены в изолированные субагенты (`context: fork`) — чтобы большие таблицы не забивали основной контекст:

| Шаг | Где | Бриф |
|---|---|---|
| 0–3, 7 (скоуп, паспорт, качество, цели, отчёт) | инлайн | — |
| 4 — источники и разметка | форк | `subagents/traffic-sources.md` |
| 5 — связка с Директом | форк | `subagents/direct-bridge.md` |
| 6 — поведение и воронки | форк | `subagents/behavior-funnel.md` |

Оркестратор читает бриф и передаёт его форку **целиком** с аргументами; форк пишет артефакты на диск и возвращает **сводку ≤20 строк**. Субагенты недоступны → выполняй те же шаги инлайн по тем же references. Брифы — инструкции, не отдельные скиллы (в пакете ровно один `SKILL.md`). Read-only в форках держится инструкцией: пишущие тулы им видны, но запрещены.

# Шаг 0. Подключение и скоуп (все режимы)

**Прочти `references/mcp-tools-map.md`.**

### Предполётная проверка (read-only, дёшево)

1. **Коннектор найден.** Ищи тул, чьё имя **оканчивается** на `yandex_metrika_counters_get` — префикс задаёт пользователь (`metrikaCM`, `MetrikaClient`…). Нет — коннектора нет: стоп, скажи, как подключить (`mcp-tools-map.md` → «Подключение»). Несколько коннекторов — спроси, какой это клиент/кабинет.
2. **Доступ живой.** `yandex_metrika_accounts_get` → есть аккаунты. Пусто или ошибка «не подключена Яндекс Метрика» → в click.ru у пользователя нет интеграции Метрики: стоп, скажи, что подключить в интеграциях click.ru (или использовать коннектор с прямым OAuth-токеном).
3. **Счётчик найден.** `yandex_metrika_counters_get({ search: "<домен>" })`. Зафиксируй `counter_id`, `permission` (own/edit/view). **`view` → Управление невозможно**, предупреди сразу.
4. **Отчёты живые.** `yandex_metrika_report({ counter_id, metrics: ["ym:s:visits"], date1: "7daysAgo", date2: "yesterday" })` → пришли числа. Ноль визитов за неделю у живого сайта — сам по себе блокер (счётчик не стоит или сломан).

Красный пункт → скажи **до старта**, что не работает и как это сузит работу.

### Скоуп — одним блоком, с дефолтами

1. **Сайт / счётчик** — если счётчиков по поиску несколько, покажи список и спроси.
2. **Период** — дефолт: последние 30 полных дней (`date1: "30daysAgo"`, `date2: "yesterday"`) + предыдущие 30 для сравнения.
3. **Что считается результатом** — какая цель = лид/продажа (макро-цель), какие — микро. Не знают — возьмём из `goals_get` и предложим.
4. **KPI** — целевой CPA / CR / ДРР, если есть. Нет — работаем по относительным сигналам.
5. **Директ** — используется ли; если да — найдём логины через `direct_clients_get`.
6. **slug** — короткое имя проекта для папки.

Формулируй гипотезой: «Беру счётчик 12345678 (site.ru), последние 30 дней к прошлым 30, результат — цель „Заявка“, Директ подтяну сам. Ок?»

**Артефакт:** `metrika/<slug>/_state.json` — `connector_prefix`, `counter_id`, `site`, `permission`, `timezone`, `period`, `compare_period`, `macro_goal_ids`, `micro_goal_ids`, `kpi`, `direct_logins`, `mode`, `current_step`.

## Шаг 0.5. Санити-чек данных (для Анализа — обязательно, коротко)

Перед ответом на вопрос в режиме Анализа сделай три дешёвые проверки из `audit-checklist.md` → «Экспресс-санити»: доля роботов, живость макро-цели (`goals_get` со `stats_days: 30`), семплирование. Красный флаг → скажи об этом **первой строкой ответа** («Осторожно: 18% визитов — роботы, конверсия занижена») и предложи полный аудит.

# Режим АУДИТ: Шаги 1–7

Только read-only: `accounts_get`, `counters_get`, `counter_get`, `goals_get`, `segments_get`, `direct_clients_get`, `report`, `report_bytime`. Пишущие тулы (`goals_add/update/delete`, `segments_add/delete`) в аудите **не вызываются**, даже с `dry_run`.

Каждый шаг пишет артефакт в `metrika/<slug>/audit/` и находки в формате `findings.json` (схема — `report-template.md`).

## Шаг 1. Паспорт счётчика

**Прочти `audit-checklist.md` → «Паспорт».**

```
yandex_metrika_counter_get({ counter_id, fields: ["goals","mirrors","grants","filters","operations","counter_flags"] })
```

Проверяешь: статус счётчика и кода, сайт и **зеркала** (поддомены, старый домен, платёжные страницы, лендинги на Тильде), **фильтры** (исключение своих IP / роботов), операции (вырезание параметров, замена домена), вебвизор/карты включены, часовой пояс совпадает с бизнесом, доступы (кто владелец, есть ли агентство/подрядчики, лишние доступы).

**Артефакт:** `01_passport.md`.

## Шаг 2. Качество данных

**Прочти `audit-checklist.md` → «Качество данных», `report-recipes.md` → R1–R4.**

- Доля роботов и её динамика (всплески по дням = бот-атака или скликивание).
- Визиты с нулевой длительностью / отказы > порога по источникам — подозрение на ботов или битую посадку.
- Домены входа (`ym:s:startURLDomain`) — чужие домены, тестовые стенды, локалхост → нужен фильтр.
- Самопереходы (свой домен в источниках-ссылках) — теряется реальный источник, ломается атрибуция (кросс-домен, платёжный шлюз).
- Доля «Прямых заходов» аномально высокая (> ~40% у сайта с рекламой) — признак потерянных меток/редиректов.
- Разрывы в динамике визитов (дни с нулём) — счётчик слетал.

**Артефакт:** `02_data_quality.md` + сырьё в `raw/`.

## Шаг 3. Цели

**Прочти `audit-checklist.md` → «Цели» и `goals-design.md`.**

```
yandex_metrika_goals_get({ counter_id, stats_days: 30 })
```

Сохрани ответ в `raw/goals.json` и прогони:

```
python -m scripts.goals_health --input metrika/<slug>/audit/raw/goals.json --visits <визиты за те же 30 дней> \
    --macro-ids <ID макро> --direct-goal-ids <ID целей стратегии Директа>
```

Ищешь: мёртвые цели (0 достижений), шумные (конверсия неправдоподобно высокая — «любой клик», «2 страницы»), дубли условий, нет макро-цели, нет составной цели под воронку, нет ценности у макро-целей, хаос в названиях, автоцели вперемешку с ручными. Отдельно — **на какую цель оптимизируется Директ** (спроси или возьми из скоупа): если на шумную/мёртвую — это находка №1 по деньгам.

**Артефакт:** `03_goals.md` + `03_goals.json`.

**[GATE]** Покажи сводку целей (5–10 строк): «Живых 6, мёртвых 3, шумных 1 — Директ, похоже, учится на шумной. Дальше — источники и Директ?»

## Шаг 5. Связка с Директом  [форк `direct-bridge`]

Пропусти, если Директ не используется (`direct_clients_get` пусто и пользователь подтвердил).

```
Запусти изолированного субагента (форк). Задача = полное содержимое
subagents/direct-bridge.md, аргументы:
  $0 = <slug>  $1 = <counter_id>  $2 = <date1..date2>  $3 = <macro_goal_ids>  $4 = <direct_logins>
```

Возвращает: сводку (потеря визитов клик→визит по кампаниям, расход и CPA по кампаниям по данным Метрики, кампании без конверсий, топ-фразы с отказами) + `05_direct.md`, `05_findings.json`.

## Шаг 6. Поведение и воронки  [форк `behavior-funnel`]

```
Запусти изолированного субагента (форк). Задача = полное содержимое
subagents/behavior-funnel.md, аргументы:
  $0 = <slug>  $1 = <counter_id>  $2 = <date1..date2>  $3 = <macro_goal_ids>  $4 = <micro_goal_ids>
```

Возвращает: сводку (страницы входа-утечки, устройства/регионы с провалом конверсии, где рвётся воронка, новые vs вернувшиеся) + `06_behavior.md`, `06_findings.json`, гипотезы для A/B.

## Шаг 7. Отчёт

**Прочти `references/report-template.md`.** Собери находки Шагов 1–6 в `findings.json` (образец — `assets/findings_example.json`) и:

```

# → АУДИТ_МЕТРИКИ_<slug>.html рядом
```

Приоритет находок: **сначала то, что ломает данные и обучение Директа** (шумная цель в стратегии, потеря визитов, роботы, нет макро-цели), потом разметка, потом поведение и рост. Каждая карточка: диагноз (числа+период+объём) → что сделать → где → как перепроверить самому → ожидаемый эффект. Язык человеческий, без `ym:s:*` в тексте.

В чат — топ-5 находок и ссылка на файл. Если есть находки по целям/сегментам — предложи: «Могу сразу переделать цели — перейдём в управление?»

# Режим АНАЛИЗ

**Прочти `references/analysis-playbook.md` и `references/report-recipes.md`.**

### Разовый вопрос

1. Шаг 0 (скоуп можно сократить до счётчика и периода) → Шаг 0.5 санити-чек.
2. Переформулируй вопрос в **метрику + разрез + сравнение** («почему упали заявки» → `goal<макро>reaches` по `lastsignTrafficSource`, этот период vs прошлый, затем вглубь по дереву разрезов из playbook).
3. Тяни отчёты по рецептам. Сырые ответы → `analysis/raw/`, через `metrika_table.py` (с `--compare` для двух периодов) → таблица с дельтами.
4. Иди по дереву разрезов, пока не найдёшь сегмент, который **объясняет большую часть изменения** (вклад в дельту, а не просто «упал сильнее всех в %»).
5. Ответ: 1 строка вывода → 3–5 строк доказательства (числа, период, объём) → что сделать → чего не знаем. Таблицы — в файл `analysis/<дата>_<тема>.md` / `.csv`.
6. Если вывод требует изменений на сайте — оформи **ТЗ** (`analysis-playbook.md` → «ТЗ»); если спорный — **A/B-гипотезу** с критериями и длительностью через `ab_calc.py`.

### Регулярный разбор (неделя / месяц)

Регулярные отчёты показывают динамику, а не разовые всплески. Состояние живёт в `metrika/<slug>/pulse.md` (что смотрим, нормы, история), поэтому разбор переживает новые сессии.

- **Первый запуск:** согласовать с человеком 5–8 ключевых метрик (визиты, доля рекламы, CR макро-цели, CPA по Директу, отказы на ключевых посадках, доля роботов), записать их нормы (среднее за 4–8 недель) в `pulse.md`. Нужна постоянная папка — попроси подключить папку проекта.
- **Каждый запуск:** период к прошлому + к норме → отклонения больше порога из `pulse.md` → разбор причин по дереву → 5–10 строк: что изменилось, почему, что делать. Дописать строку в историю `pulse.md`.
- Нет изменений за порогом — так и скажи одной строкой. Не высасывай находки.
- Если пользователь хочет, чтобы разбор шёл сам по расписанию — предложи создать запланированную задачу с промптом «продолжаем регулярный разбор Метрики <slug>».

# Режим УПРАВЛЕНИЕ (цели и сегменты)

**Перед стартом прочти `references/write-safety.md` и `references/goals-design.md` целиком.**

Требование: `permission` счётчика `own` или `edit` (см. Шаг 0). `view` → стоп, объясни, кто может выдать доступ.

## Фаза A. Снимок

`goals_get({ counter_id, stats_days: 30 })` + `segments_get({ counter_id })` → сохрани в `changes/<дата>/before.json`. Это и база для отката, и защита от дублей.

## Фаза B. Проект изменений

Из запроса пользователя, находок аудита и `goals-design.md` составь `changes/<дата>/proposed.json` — список операций. Для каждой:

- `op` (`goal_add` / `goal_update` / `goal_delete` / `segment_add` / `segment_delete`), полное тело, зачем, класс (обратимая / необратимая);
- для **цели** — проверка, что её условие реально сработает (URL страницы «спасибо» существует в отчёте `ym:s:startURL`/страниц, JS-идентификатор есть на сайте или для него пишется ТЗ разработчику);
- для **удаления цели** — проверка, не используется ли она в Директе (стратегия/ключевые цели). По умолчанию **не удаляем**, а переименовываем с префиксом `[OFF] ` — удаление необратимо и рвёт обучение кампаний;
- для **сегмента** — условие проверено отчётом с тем же `filters` (покажи, сколько визитов/пользователей попадает: пустой сегмент бесполезен для ретаргетинга).

## Фаза C. Dry-run и гейт

Каждую операцию прогони с `dry_run: true` — покажи человеку **тело запроса** и что изменится. Список: обратимые отдельно, необратимые отдельно.

**[GATE]** «Вот что создам/изменю в счётчике <id>. Применяем всё, частично или правим?» Необратимые (удаление цели/сегмента) — **отдельное подтверждение на каждую**.

## Фаза D. Применение

По одобренному, строго по `write-safety.md`: `changes_log.py record` (before) → боевой вызов → дописать after + ID. `goals_update` — только **полным объектом** (взятым из `goals_get` и изменённым), иначе Метрика сбросит пропущенные поля. Ошибка → статус `failed` в журнале, не молчи.

## Фаза E. Проверка и передача

- `goals_get` — новые цели на месте, ID записаны.
- Цели по JS-событиям — выдай **ТЗ разработчику** (`goals-design.md` → «ТЗ на JS-событие») с готовым кодом `ym(<counter_id>, 'reachGoal', '<id>')`.
- Цели не считают задним числом: попроси через 1–2 дня запустить «проверь новые цели» → `goals_get({ stats_days: 2 })`. Ноль достижений при живом трафике → условие не срабатывает, разбираем.
- Если цель для Директа — скажи, какой ID указать в стратегии/ключевых целях (это делается в Директе, не здесь).
- `changes/<дата>/change_report.md`: что сделано, ID, что ждём, как откатить.

# Стиль работы

- **Один вопрос за раз**, скоуп — одним блоком с дефолтами.
- **Гипотеза > пустой вопрос.**
- **В чат — 5–10 строк**, таблицы и сырьё — в файлы.
- **Числа с контекстом:** период, объём, сравнение, модель атрибуции словами.
- **Никаких `ym:s:*` и `lastsign` в текстах для человека** — «источник по последнему значимому переходу», «страница входа».
- **В аудите и анализе — только чтение.** Рука тянется поправить цель — стоп, это находка с предложением перейти в Управление.
- **В управлении — dry_run, гейт, журнал.** Ни одной записи без «ОК».
- **References обязательны:** «Прочти …» — требование.
