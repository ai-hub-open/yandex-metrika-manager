# Управление: безопасная запись в счётчик

Работает **только в режиме Управление**. В Аудите и Анализе запись запрещена всегда.

Главное правило: **ничего не пишется в счётчик без явного «ОК» на конкретный список изменений.** «Делай как считаешь нужным» — не «ОК» на удаление: необратимое подтверждается поштучно.

## Предохранитель 1 — снимок и journal-before-write

1. Фаза A: `goals_get` + `segments_get` → `changes/<дата>/before.json`.
2. Перед каждой записью: `python -m scripts.changes_log record --workspace metrika/<slug> --change <дата> --object-type goal --object-id <id|new> --tool goals_update --class reversible --before '<json>' --status pending`.
3. Боевой вызов → сразу после ответа ещё одна строка `--status applied --after '<json с ID>'` (или `failed` с причиной в `--note`).

## Предохранитель 2 — dry_run → показ → запись

Все пишущие тулы Метрики поддерживают `dry_run`. Первый вызов любой операции — `dry_run: true`; покажи человеку тело запроса. Только после «ОК» — тот же вызов без `dry_run`.

## Предохранитель 3 — обратимые vs необратимые

| Операция | Тул | Класс | Before | Откат |
|---|---|---|---|---|
| Создать цель | `goals_add` | обратимая* | — | удалить созданную (только если ни на что не завязана) |
| Изменить цель | `goals_update` | обратимая | полный объект из `goals_get` | `goals_update` с before |
| «Выключить» цель | `goals_update` (имя → `[OFF] …`) | обратимая | полный объект | вернуть имя |
| Удалить цель | `goals_delete` | **необратимая** | полный объект | только создать заново — **новый ID, истории нет**, Директ теряет цель |
| Создать сегмент | `segments_add` | обратимая | — | удалить созданный |
| Удалить сегмент | `segments_delete` | **необратимая** | полный объект | создать заново — новый ID, ретаргетинг в Директе надо перепривязать |

\* созданная цель сразу начинает копить статистику — удаление потом уже теряет данные.

Необратимое — **отдельное подтверждение на каждую операцию** с объяснением последствий («кампании Директа, оптимизирующиеся на цель 123, потеряют её»).

## Предохранитель 4 — правила для целей

- `goals_update` — **только полным объектом**: взять из `goals_get`, изменить нужное поле, отправить целиком. Иначе Метрика сбросит пропущенные поля (условия, ценность).
- Перед `goals_add` — проверка на дубль по условиям в `before.json`.
- Перед изменением/удалением — спросить, не используется ли цель в Директе (стратегия, ключевые цели, корректировки). Скилл этого сам не видит.
- Удаление по умолчанию заменяется на `[OFF]`-переименование.
- Не больше ~10 операций за один заход: длинный список — разбить на партии с гейтом.

## Предохранитель 5 — проверка после записи

- Сразу: `goals_get` / `segments_get` — объект есть, условие то, что одобрено.
- Через 1–2 дня: `goals_get({ stats_days: 2 })` — есть достижения при живом трафике. Ноль → условие не срабатывает (URL не тот, JS-событие не внедрено) — разбирать.
- Сегмент — размер по R20.

## Порядок применения

1. Сортировка: создание → изменение → `[OFF]` → необратимое (с отдельным конфирмом).
2. Каждая операция: log pending → вызов → log applied/failed.
3. Ответ проверять целиком; `success: false` или пустой ID — `failed`, не выдумывать успех.
4. `applied.json` + `change_report.md`: что сделано (с ID), что отклонено, что ждём (ТЗ разработчику, проверка через 1–2 дня), как откатить (`changes_log rollback-plan`).
